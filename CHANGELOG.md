# Changelog

What changes for the people who use the Visual Studio extension and the packages (`Abstractions.Sass.CIBuild`, `Abstractions.Sass.CrossPlatformLibSass` and `Abstractions.Sass.CrossPlatformChakraCore`). The changelog starts after 1.1.72: the changes before it are not recorded here.

## Unreleased (2.0, beta)

## 2.0.4

2.0.3 was published to nuget.org, but not to the Visual Studio Marketplace or GitHub: the publishing tool of the build agent could not sign in, as it could not load an assembly it needs. 2.0.4 is the same release, published to all three, so these are the changes since 2.0.2.

### Added

- **The documentation and the changelog of each release are on GitHub, at [github.com/Abstractions-AS/sass-compiler](https://github.com/Abstractions-AS/sass-compiler).** Each release adds its documentation, the READMEs of the packages and the changelog there, with a GitHub release that has the changes of the version. The page of the extension on the Visual Studio Marketplace links to it, as do "More info" and "Release notes" in Visual Studio's extension manager, and `Abstractions.Sass.CIBuild` names it as its repository on nuget.org. The source is not on GitHub.

## 2.0.2

2.0.1 was published with the release notes of 2.0.0, so these are the changes since 2.0.0: the byte order mark was fixed in 2.0.1, and the names of new files in 2.0.2.

### Fixed

- **Compressed CSS with a character outside ASCII starts with one byte order mark (BOM).** Sass starts such CSS with a BOM (in place of `@charset`), and the compiler wrote the file with a BOM of its own, so the file had two. A browser reads the second as part of the first rule, and drops that rule: with an icon font, whose glyphs are such characters, that could be its `@font-face`, so the icons of that font did not show, or a `:root` rule of Bulma 1.0. It affected both runtimes, in compressed mode (the default style) only: expanded CSS starts with `@charset "UTF-8";`. The CSS is now written with one BOM. A CSS file is only compiled again when its Sass or `sassconfig.json` changes, so to rewrite the CSS that has two, delete it, or save `sassconfig.json`, and build. This was checked with the tests, and with `dotnet build` and the MSBuild of Visual Studio 2022 and 2026; it was not tried in the Visual Studio extension.
- **A new CSS file, its source map and its folders are named as `sassconfig.json` names them.** On Windows, the compiler wrote a new output in lower case: `"outputFile": "wwwroot/Css/DatePickers.css"` became `wwwroot/css/datepickers.css`, in Visual Studio and in a build. Windows does not mind, but a case-sensitive file system, as on Linux or in Docker, does not find the file by its name once the folder is committed or copied there, so a reference to `DatePickers.css` failed. A build on Linux named it right. An output that exists already keeps its name, as Windows keeps the name of a file that is written again: rename one that is in lower case once (in git, `git mv -f`). Checked with tests of the compiler and of the build task, with LibSass and DartSass.

## 2.0.0

2.0 adds templates, icon fonts and a clean start to the Visual Studio extension. A LibSass file with `@use` or `@forward` now fails to compile, where it compiled to broken CSS without an error, so a build that passed can fail now (see Fixed); the CSS of a file that compiles does not change.

### Changed

- **The Sass Compiler menu of a project is below Add, Manage NuGet Packages and Manage Client-Side Libraries.** It was near the top of the menu, among Build, Rebuild, Clean, Publish and the commands of other extensions, where it was hard to find. The menu on Sass files and on `sassconfig.json` has not moved. In a Web Site project (the old kind, without a project file) it has not moved.

### Added

- **Sass Compiler › Add icon font adds Font Awesome, Material Symbols or Bootstrap Icons to a project.** It is shown on the project and on `sassconfig.json` when `sassconfig.json` has a file to compile, and adds the font to the first file in it. It downloads the Sass and the fonts of the icon font from jsDelivr into `Styles/lib` and adds them to `libman.json` (Font Awesome 6.7.2 for LibSass and 7.3.1 for DartSass, chosen by the runtime of the file; Material Symbols 0.49.0, outlined only; Bootstrap Icons 1.13.2); adds the target `CopyWebFonts` to the project file, which copies the fonts to `wwwroot/fonts` before the build, so that `dotnet publish` has them too, and a `WebFonts` item for the font, in an `ItemGroup` labelled `WebFonts`; writes `Styles/font-awesome.scss`, `Styles/material-symbols.scss` or `Styles/bootstrap-icons.scss`, which sets the font path to `/fonts` and imports the font; and imports that file in the main Sass file. Every step is only done when it is not done already, and the rest of the project file is kept as it is: its formatting, comments, line endings and BOM. Commit `Styles/lib`, as a build server needs the fonts. Every font was added to new projects of `dotnet new web` with LibSass and DartSass, from the real packages: they compile, `dotnet build` copies the fonts, a clean `dotnet publish` has them, and LibMan restores the same files. It was also tried in Visual Studio.
- **Sass Compiler › Cleanup VS template... removes what the ASP.NET Core project templates put in `wwwroot`.** After asking, and saying how many files and which libraries, it moves `wwwroot/lib` and every `.css`, `.js` and `.map` file in the rest of `wwwroot` to the Recycle Bin, and removes the folders that are left empty; images and `favicon.ico` are kept, and the layout is not changed. It is shown for web projects that have `wwwroot` and no `sassconfig.json`, so it comes before Initialize with, and does not remove what Initialize with wrote. What it removes was checked on new projects of `dotnet new mvc`, `webapp` and `blazor` (62, 62 and 45 files; `favicon.ico` or `favicon.png` is left); the menu item, the confirmation and the Recycle Bin were tried in Visual Studio.
- **In a Blazor project, Initialize with adds the default error and loading styles of Blazor.** A project with `.razor` files (a Blazor Web App, Blazor WebAssembly, or a Razor class library with components) gets `Styles/blazor.scss` with every template, with the styles that the Blazor templates have in `app.css` (`#blazor-error-ui`, `.blazor-error-boundary`, `.loading-progress`, `.loading-progress-text`), and `Styles/style.scss` imports it after the framework, with `@use` for the templates that compile with DartSass and `@import` for LibSass; a `style.scss` or `blazor.scss` that is there already is left as it is. The output of the extension says to remove the styles from `wwwroot/app.css`. Which projects count as Blazor was checked on new projects of `dotnet new blazor`, `blazorwasm` and `razorclasslib` (Blazor) and `mvc`, `webapp` and `web` (not), and the styles compile with LibSass and DartSass in every template; it was tried in Visual Studio.
- **Sass Compiler › Initialize with › Pico CSS 2.1.1 (Dart Sass) sets up a web project with [Pico CSS](https://picocss.com),** which styles the HTML elements with few classes. As the Bulma templates do, it downloads the Sass sources of Pico (`scss/**`, and its license) from jsDelivr into `Styles/lib/pico`, adds them to `libman.json`, and writes `Styles/style.scss`, which uses Pico and is compiled to `wwwroot/style.css` with DartSass, as Pico is written with `@use`. Its settings, such as `$theme-color` and `$enable-classes`, are set with `@use ... with (...)`, as the example in the file shows. The download and compiling it, with the example switched on, were checked against the real Pico 2.1.1; LibMan restores the same files and one more, `scss/postcss.config.min.js`, which jsDelivr makes and the Sass does not use. It was tried in Visual Studio.
- **Sass Compiler › Initialize with › Bootstrap 5.3.9 sets up a web project with [Bootstrap](https://getbootstrap.com).** As the Bulma 0.9.4 template does, it downloads the Sass sources of Bootstrap (`scss/**`, and its license) from jsDelivr into `Styles/lib/bootstrap`, and its JavaScript (`bootstrap.bundle.min.js`, with its map) into `wwwroot/js/lib` (out of `wwwroot/lib`, which Cleanup VS template removes; the layouts of the ASP.NET Core templates load it from `~/lib/bootstrap/dist/js/`, so change the script to `~/js/lib/bootstrap.bundle.min.js`), adds them to `libman.json` (with `fileMappings`; the libraries in it are kept), and writes `Styles/theme.scss`, with examples of how to set Bootstrap's variables and add a theme color, and `Styles/style.scss`, which imports the theme and Bootstrap and is compiled to `wwwroot/style.css` with LibSass. `wwwroot/style.css` has all of Bootstrap, so a layout that links the CSS of Bootstrap (the ASP.NET Core templates link `~/lib/bootstrap/dist/css/bootstrap.min.css`) should link `~/style.css` instead; the output of the extension says so. A `bootstrap.bundle.min.js` that is there already is left as it is. The download, the files, and compiling them with LibSass and DartSass, with the examples of the theme switched on, were checked against the real Bootstrap 5.3.9, and LibMan 3.0.71 (Visual Studio 2022) and 3.0.114 (Visual Studio 2026) restore the same files, the JavaScript included; it was tried in Visual Studio.
- **Sass Compiler › Initialize with › Empty template (libsass) or Empty template (dart-sass) sets up a web project for Sass.** Right-click an ASP.NET Core project, a Razor class library or a Blazor project that has no `sassconfig.json`, and it writes `Styles/style.scss` with an empty rule and a `sassconfig.json` that compiles it to `wwwroot/style.css`, with `sassconfig.json.defaults` next to it, compiles it (`wwwroot/style.css` is empty until the Sass has rules; Empty template (dart-sass) sets `"runtime": "DartSass"` for it, for Sass with `@use`), opens the Sass file, and turns on compile on build, which adds `Abstractions.Sass.CIBuild` from nuget.org, as Enable compile on build does; if the package is in the project already, it is left as it is. Before, the only way to start was to right-click a Sass file that already existed and choose Compile file. A `Styles/style.scss` that exists already is not overwritten. The menu is not shown for other kinds of projects, or once the project has a `sassconfig.json`. The menu and the files were tried in Visual Studio.
- **Sass Compiler › Initialize with › Bulma 0.9.4 (recommended) or Bulma 1.0.4 (Dart Sass) sets up a web project with [Bulma](https://bulma.io).** For 0.9.4: It downloads the Sass sources of Bulma 0.9.4 (and its license, but not its CSS) from jsDelivr into `Styles/lib/bulma`, and adds Bulma to `libman.json`, which is created if the project has none, with the files as patterns (`"sass/**"`); the other libraries in it are kept. `libman.json` is written as version 3.0, the version of LibMan in Visual Studio 2022 and 2026, and one of a lower version, or without a version, is set to 3.0. It writes `Styles/theme.scss`, with examples of how to set Bulma's variables and add a color, and `Styles/style.scss`, which imports the theme and Bulma, and compiles it to `wwwroot/style.css` with LibSass, the default. Then, as Empty does, it opens the Sass file and turns on compile on build. Commit `Styles/lib/bulma`: a build server needs the Bulma files to compile. If `libman.json` has Bulma already, in any version, it is left as it is and nothing is downloaded. Nothing is written when the download fails. 1.0.4 does the same with Bulma 1.0.4, which is written with `@use` and only compiles with DartSass, so its `sassconfig.json` sets `"runtime": "DartSass"`; it writes only `Styles/style.scss`, with an example of how to set Bulma's variables with `@use ... with (...)`. Its CSS is about 690 KB, against about 210 KB for 0.9.4. Both write `Styles/validation.scss`, which `style.scss` imports after Bulma, to style the validation of ASP.NET Core with Bulma: a red or green border on invalid and valid fields, a red `*` after the label of a required field, the messages as help text, and the list of errors as a danger notification; for 1.0 with the custom properties of Bulma, so that it follows its themes and the dark mode. The downloads, the files, and compiling them were checked against the real Bulma 0.9.4 (with LibSass and DartSass) and 1.0.4 (with DartSass), and LibMan restores the same files from the `libman.json` that is written; it was tried in Visual Studio.

### Fixed

- **With LibSass, `@use` and `@forward` are an error.** LibSass, the default runtime, does not have the module system of Dart Sass, and wrote `@use` and `@forward` to the CSS as they were, without an error, so the CSS was broken and nothing said why; a library written for Dart Sass (such as Bulma 1.0 or Pico CSS) compiled to a few bytes of useless CSS. Now the compile fails with "LibSass does not support @use and @forward", on the line of the rule, or on the file when the rule is in a file it imports, as the Error List and a build show other errors. Set `"runtime": "DartSass"` for the file in `sassconfig.json`, or for every file in `sassconfig.json.defaults`. A rule in a comment does not count. No file that compiled to working CSS fails now: CSS has no `@use` or `@forward` rules.

## 1.1.75

### Changed

- **"Enable compile on build" adds the package without asking first.** It showed a message that a package would be added, which had to be closed before anything happened; the status bar says what happens as the package is added or removed, and the "Abstractions Sass Compiler" pane of the Output window says what the package does, without opening or taking the focus. The menu items are "Enable compile on build" and "Disable compile on build", without the "..." that promised a dialog.

### Added

- **`Abstractions.Sass.CIBuild` brings an agent skill for AI coding agents.** A skill tells an agent such as Claude Code or GitHub Copilot how the compiler works: `sassconfig.json` and its options, that LibSass, the default, has no `@use` or `sass:math`, how urls are written, and how the build reports an error. When the repository already has a `.claude` or `.agents` folder, the build copies the skill into its `skills` folder (the nearest one, from the project up to the root of the repository), and writes it again only when an update of the package changes it. A repository without such a folder gets nothing, and the folder of the user (`~/.claude`) is never written to. Set `SassAgentSkills` to `False` to turn it off. `HerreruudAgentSkills` (`claude`, `agents` or `all`), as the Herreruud.Framework packages read it, chooses the folders instead. This was checked with `dotnet build` and the MSBuild of Visual Studio 2022 and 2026; whether an agent picks the skill up from a `.claude` folder below the root of the repository depends on the agent.

### Packages

- **`Abstractions.Sass.CIBuild` is added with `PrivateAssets="all"`.** It is a development dependency, so NuGet writes `PrivateAssets="all"` when the package is added, from Visual Studio, `dotnet add package` or the extension's "Enable compile on build". Without it, a project that is itself packed as a NuGet package made it a dependency of its own package, and the projects that used that package got the Sass build step too. A reference that was added before does not change: add `PrivateAssets="all"` to it yourself. This was checked with `dotnet add package` and with Manage NuGet Packages in Visual Studio, with a prerelease of the package. "Enable compile on build" adds the version from nuget.org, so it writes `PrivateAssets="all"` once this release is there.
- `Abstractions.Sass.CIBuild` is about 2 MB smaller: it no longer carries `System.Linq.Async`, which nothing in it used.

## 1.1.74

1.1.73 was built, but not published to nuget.org or the Visual Studio Marketplace, so these are the changes since 1.1.72.

### Changed

- **A `url()` is written to the CSS as it is in the Sass, unless `rewriteUrls` is on.** The compiler rewrote relative urls to be relative to the CSS file, and the CSS it wrote for them was broken: the closing parenthesis was missing, the quotes and any query (`?v=4`) were dropped, the path was one folder short and in lower case on Windows. In compressed CSS, the default, this happened to almost every relative url, also a bare file name such as `url(logo.png)`, as soon as a `/` came anywhere after it in the file (a `font: 12px/1.5` is enough), and the missing parenthesis could take the next rule with it. A url is now written as it is, as other Sass compilers do and as libraries such as Font Awesome and Bootstrap Icons expect: a relative url is relative to the CSS file. Urls that start with `/`, data urls and urls with a scheme were not changed before and are not now. No working CSS changes: every url that the compiler rewrote was broken.

### Added

- **`rewriteUrls`, to write relative urls from the Sass file.** Set `"rewriteUrls": true` for a file in `sassconfig.json`, or for every file in `sassconfig.json.defaults`, and a relative url is read as relative to the Sass file and rewritten to be relative to the CSS file: `url(images/logo.png)` in `Styles/site.scss`, compiled to `wwwroot/css/site.css`, becomes `url(../../Styles/images/logo.png)`. The quotes, the query and the fragment are kept, and so is the case of the path; a path with a space in it is put in quotes. Urls that start with `/` or `#`, and urls with a scheme (`data:`, `https:`), are not changed. The compiled CSS does not say which file a url came from, so a url in an imported partial is read as relative to the main Sass file, not to the partial. Visual Studio suggests the setting in both files.
- **The extension declares Visual Studio 2026.** Its install range is now Visual Studio 17.0 and later. Visual Studio 2026 already installed and ran it, as it takes extensions built for Visual Studio 2022.

### Fixed

- **The paths in `sassconfig.json` are relative to its folder, whatever the current directory is.** The check for whether a file needs compiling, and the `loadPaths` given to LibSass and DartSass, used the current directory of the process. A build runs in the folder of the project, so it worked there, but:
  - with DartSass, a relative load path did not work for the second project that a build process compiled (an MSBuild node is reused for the next project of a solution): the import failed with "Can't find stylesheet to import";
  - where the current directory is not the project, as it can be in Visual Studio, a relative load path failed, and the check looked for the files in the wrong folder and compiled every file again.
- **A change to `sassconfig.json` or `sassconfig.json.defaults` compiles the files again.** A file was only compiled again when it or a file it imports had changed, so a new option, such as another `style`, did nothing until a Sass file changed. That was also true of a build. Saving either file in Visual Studio now compiles with the new options.
- **A partial that is imported through `loadPaths` is a dependency.** A change to it did not make the CSS out of date, in a build or when it was saved in Visual Studio, so the CSS could be old. An import is now looked for next to the importing file and then in the load paths, as Sass does, and the imports of a partial in a load path outside the project are followed too.
- **A changed partial in a second project is noticed.** The files that each Sass file imports were kept for the first project that a process compiled, and used for every project after it. In Visual Studio, saving a partial in another project with Sass did not compile the files that import it, and a build process that compiled several projects could miss a change to a partial and leave the CSS old. Each project now has its own.
- **An import that is added to a partial, or removed from it, counts at once.** The imports of a partial were read once and kept for as long as the process ran: a whole session in Visual Studio, and an MSBuild process that is kept for the next builds. A partial that a partial started to import was not a dependency until then, so a change to it did not compile the files that use it, and the CSS stayed old until Visual Studio was restarted or the build process had stopped. A file that has been written since it was read is now read again before its imports are used.
- **An unchanged source map is not written again.** With `sourceMap` on, the `.map` file was written on every compile, as if it had changed, so file watchers saw a change and Visual Studio checked it out of source control each time. It is now written when it changes, as the CSS file is. In Visual Studio, a map file that has been taken out of the project is no longer put back on every compile, only when it changes, as for the CSS file.

### Packages

- **`Abstractions.Sass.CIBuild` depends on no package.** It carries the compiler and everything it uses in its `tools` folder, but it also declared a dependency on DartSassHost, so a project that used it without `PrivateAssets="all"` got DartSassHost and JavaScriptEngineSwitcher.Core as packages of its own, which it does not use. `PrivateAssets="all"` is still a good idea, so that a project that is itself packed does not pass the package on.
- The README of `Abstractions.Sass.CIBuild` says that the package runs in the 64-bit MSBuild only (`dotnet build`, Visual Studio, `MSBuild\Current\Bin\amd64\MSBuild.exe`). The 32-bit `MSBuild\Current\Bin\MSBuild.exe` could never load its native libraries.
- `Abstractions.Sass.CrossPlatformChakraCore` has a README and an icon, and the three packages name Abstractions AS as their author.
- The README of `Abstractions.Sass.CIBuild` names the defaults file correctly (`sassconfig.json.defaults`, not `sassconfig.default.json`), and says how to turn the build step off (`<RunSassCompiler>False</RunSassCompiler>`).
